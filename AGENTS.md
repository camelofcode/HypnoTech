# HypnoTech repository guidance

## Purpose and scope

This repository is the reusable HypnoTech ASP.NET Core engine. Its modules are CMS,
Common, Ecommerce, Media, Frontend, and MongoDB persistence. `HypnoTech.slnx` is the
authoritative solution map; projects are physically grouped under `src/Cms`,
`src/Common`, `src/Ecommerce`, `src/Media`, `src/Frontend`, and `src/Persistence`.

Work only in this engine repository. Do not edit or copy content, configuration, seed
data, branding, or imagery from private client websites. Treat those sites as external
production consumers. Additional payment-provider work in
`ecommerce-payments-plan.md` is deferred.

## Compatibility rules

- Preserve public namespaces, assembly names, routes, action behaviour, static asset
  paths, and DI extension semantics unless a reviewed breaking change is authorised.
- Preserve MongoDB collection names and BSON member names unless a tested data migration
  and rollback plan is part of the change.
- Treat engine commit `95c9f6a`, MongoDB.Driver 3.4.3, and MongoDB Server 4.0.3 as the
  production compatibility baseline.
- Add characterisation tests before changing dynamic CMS mapping, controller, form,
  route, registry, repository, search, paging, child-population, or ordering behaviour.
- Use native async provider APIs for I/O; do not introduce `Task.Run`, `.Result`,
  `.Wait()`, or `GetAwaiter().GetResult()` into request paths.
- Keep public repository and I/O-bound service contracts async-only. The production
  sites consume the preserved support branch, not public `main`.
- Keep required browser assets self-hosted and versions pinned.

Run the `cms-compatibility-review` skill before implementing a change that affects the
dynamic CMS pipeline, persistence mappings, repository contracts, public routes, or
stored data. Run `verify-engine-change` after implementation to choose and execute the
checks appropriate to the changed paths.

Run the `author-characterisation-tests` skill when adding or changing unit,
integration, architecture, or future browser tests. It defines the shared conventions
for synthetic fixtures, static registry isolation, MongoDB compatibility targets, and
characterisation-first assertions.

Run the `test-external-http-integrations` skill when testing an outbound HTTP client or
third-party SDK adapter. It defines the local protocol-stub boundary, safety rules,
failure coverage, and dependency policy; automated tests must never contact live or
sandbox providers.

Run the `author-async-request-paths` skill when adding or revising controllers,
services, repository contracts, or persistence implementations. It defines the
project's inheritance, module-boundary, native-async, cancellation, and async-only
contract conventions.

Run the `release-engine` skill when preparing a numbered release, choosing its SemVer
increment, updating release metadata/notes, tagging verified `main`, or publishing the
GitHub Release. It keeps GitHub source releases separate from NuGet publication and
production deployment.

## Source and generated assets

Authored browser source is under the frontend-asset directories such as
`src/Cms/HypnoTech.Cms.Frontend/js` and `scss`; third-party snapshots are under their
`lib` directories. Runtime bundles under `src/**/wwwroot` are generated by
`tools/build-frontend.mjs` and committed for .NET consumers.

Never edit a generated `wwwroot` bundle directly. Change its source, run
`npm run build:frontend`, inspect both source and output, then run
`npm run check:frontend`.

## Standard commands

```bash
dotnet restore HypnoTech.slnx -m:1
dotnet build HypnoTech.slnx -c Release --no-restore -m:1
./tests/run-solution-tests.sh
npm ci
npm run check:frontend
```

Run tests once the relevant projects exist; do not report an absent suite as passed.
Prefer the smallest relevant test selection during iteration, followed by the full
required checks before handoff. Record commands, results, skips, and remaining gaps.

## Change discipline

Keep mechanical moves, dependency updates, behavioural changes, and formatting changes
separate. Do not reformat unrelated legacy code. Preserve user changes in a dirty tree.
The completed public-readiness plan under `docs/archive/` is historical and must not be
used as a living work log. Create or update a purpose-specific current plan when future
work genuinely needs one.
